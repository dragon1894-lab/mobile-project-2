# 김하균 서버 파트 공동 작업 기록 — Codex ↔ Claude

이 파일은 김하균님이 Codex와 Claude 사이에서 작업을 이어가기 위한 **공유 기록**이다. 두 AI의 채팅은 자동으로 연결되지 않는다. 각자 이 Git 저장소의 최신 커밋과 이 파일을 읽고, 작업 결과·의견·검증 근거를 기록한다. 팀원에게 보낼 내용은 먼저 **김하균님에게** 전달한다. 다른 AI나 팀원에게 직접 메시지를 보내는 용도가 아니다.

## 시작할 때 읽는 순서

1. `AGENTS.md`, 이 파일, `docs/PROJECT_HANDOFF.md`, `docs/SOURCE_AUDIT_2026-10-13.md`를 읽는다.
2. `git status`, 현재 브랜치와 최신 커밋, 실제 프로젝트 파일을 확인한다. 이 문서의 상태보다 **실제 코드와 검증 결과**를 우선한다.
3. 다른 AI가 올린 코드가 있다면 변경 파일·API 호환성·DB 이관·빌드/테스트 결과를 확인한다. 확인하지 않은 작업을 완료로 표시하지 않는다.
4. 작업 뒤에는 아래 현황과 작업 기록을 갱신하고, 조원에게 전달할 내용을 김하균님에게 짧고 쉽게 설명한다.

## 지금까지 정해진 프로젝트 방향

- 사용자: **김하균**, 5명 중 3번. 담당은 서버·DB·유선 이더넷 통신·공용 API 계약·전체 통합.
- 현재 기준 문서: `CSharp_생산라인_검사_AI상담_통합기획서_v5_역할분담.pdf`와 사용자 후속 결정. 이전 v2와 별도 5팀 사례의 기술 구성을 섞지 않는다.
- 관리자(조영준)와 작업자(문성찬)는 **각각 C# WinForms**를 만든다. 두 앱은 같은 ASP.NET Core 서버의 REST/JSON API를 사용하며 DB에 직접 접속하지 않는다.
- 영상처리(장서진)는 OpenCvSharp로 LINE 1의 형태·윤곽/색상 검사와 정상·불량·판정 불가 결과를 만든다. AI가 품목을 판정하지 않는다.
- 상담·업무 흐름(공도현)은 문제 발생 이후 매뉴얼 근거의 AI 안내를 만든다. 관리자 문의는 사람과 사람의 대화이며, AI 상담과 구분한다. AI가 설비를 제어하거나 문제를 종결하지 않는다.
- LINE 1만 대표 실제 상세 기능이고 LINE 2~4는 가상 대시보드 데이터다.
- 문제 흐름: 발생 → 사용자 확인 → 조치 중 → 완료 요청 → 관리자 확인 → 종결. 서버가 권한과 상태 전이를 검증하고 변경 이력을 남긴다.

## 네트워크와 기존 공용 코드: 용어까지 함께 설명할 것

- 서버의 `0.0.0.0:5050`: **서버 PC의 모든 네트워크 주소에서 5050번 요청을 받는다.** 서버를 다른 PC로 옮겨도 일반적으로 이 값을 그 PC의 IP로 바꾸지 않는다.
- 윈폼의 기본 `127.0.0.1:5050`: **윈폼을 실행한 자기 PC**를 가리킨다. 서버와 윈폼을 같은 PC에서 켰을 때 사용한다.
- 팀원 PC의 접속 주소: **실제로 서버를 실행하는 PC의 IP**와 포트. 예: `http://<서버PC-IP>:5050`. 2026-10-16 대화에서 확인한 `192.168.0.9`는 당시 김하균님 PC의 Wi-Fi IP일 뿐이며 고정 주소나 연결 검증 결과가 아니다. `192.168.0.107`은 앞선 설명용 예시였다.
- 현재 공용 클라이언트 `00_Shared/ProductionLine.Shared/ProductionLineApiClient.cs`는 생성자 인수 → `PRODUCTIONLINE_SERVER_URL` 환경변수 → `http://127.0.0.1:5050` 순서로 주소를 정한다. 따라서 다른 PC 접속을 위해 C# 파일을 직접 고칠 필요는 없다.
- `Contracts.cs`는 양쪽이 주고받는 DTO, `ProductionLineApiClient.cs`는 서버 호출 **함수들이 들어 있는 파일**이다. 함수 예: `LoginAsync(userId, password)`. 관리자·작업자 WinForms의 입력/버튼/표시 코드는 각 앱 담당이 맡고, 서버의 인증·권한·처리·저장은 김하균 담당이다.
- 팀원 접속에는 서버 실행, 실제 포트 확인, 네트워크 도달, 방화벽 허용이 필요하다. Visual Studio의 `https` 시작 프로필이 보였지만 그 프로필의 실제 바인딩과 두 PC 통신은 **아직 검증되지 않았다**.
- 관리자 PC와 작업자 PC **2대**가 최소 시연 구성이다. 서버를 관리자 PC에서 함께 실행하면 2대이고, 서버를 별도 PC에서 실행하면 3대다. 팀원이 5명이라고 PC 5대가 필요한 것은 아니다. 두 앱은 어느 배치에서든 같은 서버 한 대를 바라봐야 한다.

DB인 **10번은 B·C·D에 걸친 공통 저장 방식**이다. 5~9번이 전부 단순 저장 작업인 것은 아니다. 8번은 관리자와 사람 간 문의·답변, 9번은 AI 모듈 호출·답변이다. 작업자 앱에서 어느 버튼/탭을 눌렀는지에 따라 각각 다른 서버 기능을 호출하며 서버가 문자열 뜻만 보고 목적지를 추측하지 않는다.

처음 배우는 사람에게는 아래처럼 설명한다. **서버는 요청 받기 → 로그인·권한 확인 → 처리·저장 → 결과 반환**, DB는 정보를 보관하는 곳, WinForms는 입력·버튼·화면이다. 3번 인증은 “누구인가”, 4번 권한은 “그 사람이 이 기능/라인에 접근해도 되는가”다. 11번 계약은 윈폼이 **보내는 값과 서버가 돌려주는 값 둘 다**를 뜻한다. 현재 저장소가 JSON 파일인 것과 API가 JSON으로 통신하는 것은 별개다. DB를 SQLite로 바꿔도 REST/JSON 계약은 유지할 수 있다.

기존 초안의 주요 호출은 `LoginAsync` → `POST /api/auth/login`, `GetLinesAsync` → `GET /api/lines`, `GetUsersAsync`/`CreateUserAsync` → `GET`/`POST /api/users`, `GetInspectionsAsync`/`SimulateInspectionAsync` → `GET /api/inspections`/`POST /api/inspections/simulate`, `GetIssuesAsync`/`CreateIssueAsync`/`UpdateIssueAsync` → 문제 조회·등록·상태 변경, `ConsultAiAsync` → `POST /api/ai/consult`다. **별도 관리자 문의/답변 API와 조회 함수는 아직 없다.** 실제 필드와 오류 응답은 코드가 제공되면 `Contracts.cs`, `ProductionLineApiClient.cs`, 서버 `Program.cs`로 다시 확인한다.

AI와 DB 연결은 두 수준을 구분한다. 새 조치·문의·매뉴얼 기록을 DB에서 읽어 **다음 상담의 참고 정보로 제공**하는 것은 가능하다. 이것이 모델 자체를 실시간 재학습한다는 뜻은 아니다. 현재 초안은 네 가지 고정 매뉴얼의 키워드 검색만 한다. AI가 DB에서 최신 자료를 조회할 범위와 기록 보존 정책은 구현할 때 합의한다.

## 확인된 현재 상태와 아직 하지 않은 일

- **Git 저장소:** 현재 문서만 있다. 앞서 받은 C# 소스 압축파일은 정적 검토했지만 이 저장소에 아직 가져오지 않았다. 새 코드가 올라오면 먼저 `git status`와 파일 목록으로 확인한다.
- **압축파일의 초안:** 6개 C# 프로젝트(Shared, AdminApp, UserApp, Server, Vision, AiAssistant)가 있었다. 로그인, 사용자 등록, 검사·문제 기본 API, 일부 WinForms 호출은 연결되어 있었다. 초안은 서버의 `data/store.json` 파일에 계정·라인·검사·문제를 저장한다. 초기 아이디/비밀번호는 시연 편의를 위해 윈폼에 채워져 있으며 서버는 비밀번호 해시와 비교한다.
- **미완성:** EF Core·SQLite DB, 새 권한의 즉시 반영, 상태 전이/조치 감사 이력, 별도의 관리자 문의·답변 저장, AI 대화 저장, 실제 영상 분석의 서버 연결, 두 PC 실행 검증 등. 현재 상담은 고정 매뉴얼 키워드 방식이며 검사 버튼은 점수 시뮬레이션이다.
- **검증 수준:** 압축파일의 작성 소스·설정·JSON을 정적 검토했다. DLL/EXE 내부 분석 및 실제 전체 빌드·윈도우 실행·두 PC 연결은 완료하지 않았다. 상세 근거는 `docs/SOURCE_AUDIT_2026-10-13.md`에 있다.
- **다음 착수:** 사용자가 실제 프로젝트 코드 또는 Claude의 변경 코드를 제공하면 원본·현재 Git 상태를 대조한다. 기존 서버/API를 기반으로 동작 기준을 확인하고, A 계약 → B 계정·권한/DB → C 검사 → D 문제·상담 → E 통합 순으로 진행한다.

## Codex와 Claude가 의견을 주고받는 규칙

- **사실 / 제안 / 결정 / 검증 결과를 구분한다.** 제안을 이미 구현했거나 팀이 합의한 사실처럼 쓰지 않는다. 사용자 결정은 두 AI의 의견보다 우선한다.
- 기존 구현을 검토할 때는 해당 커밋·파일·API·DB 영향·검증 결과를 근거로 **유지 / 작은 수정 / 방향 변경 제안** 중 하나를 기록한다. 취향만으로 이미 작동하는 코드를 다시 만들지 않는다.
- API 호환성, 저장 데이터 이관, 담당 영역, 보안·권한, 전체 구조가 바뀌는 이견은 양쪽 의견과 장단점·영향 범위를 이 파일에 적어 **김하균님에게 먼저 설명한다**. 사용자가 방향을 고르면 결정 기록에 남기고 그 방향으로 진행한다. 일상적인 오탈자·작은 수정은 기존 위임 범위에서 바로 처리한다.
- 동시에 같은 파일을 고칠 경우 Git의 최신 상태를 먼저 확인하고 자기 변경과 타인의 변경을 구분한다. 다른 AI의 미반영 작업을 덮어쓰지 않는다. 새 코드가 Git에 없고 사용자가 파일로 전달한다면 실제 내용을 비교한 후 반영 여부를 판단한다.
- 각 작업 완료 뒤 코드 커밋/상태, 통과·실패·미실행 검증, 다음 할 일과 **김하균님이 조원에게 보낼 연결 안내**를 기록한다. 사용자가 기존에 허용한 Git 업로드 흐름으로 공유하되, 팀원에게 직접 연락하지 않는다.
