# SQLite DB 클래스 8개 — 이름과 역할 정리

수정 기준: 2026-10-18에 확인한 서버 코드. 기존 ‘DB 클래스 7개’ 문서를 현재 구조에 맞게 갱신했습니다.

## 지금 만든 구조

DB에 저장할 정보의 형태를 정하는 클래스 **7개**와, EF Core에서 DB를 다루는 `AppDbContext` **1개**입니다.

정보 클래스 7개는 각각 DB 테이블 하나에 대응합니다. 클래스 안의 속성은 테이블의 열(저장 항목)에 대응합니다. `AppDbContext` 자체는 테이블이 아닙니다.

즉, **테이블 7개 + DB 관리 클래스 1개 = 클래스 8개**입니다. EF Core가 별도로 사용하는 마이그레이션 관리 테이블은 이 업무용 테이블 개수에 포함하지 않습니다.

파일 위치: `03_Server/ProductionLine.Server/Data/`

## 1. UserEntity.cs — 사용자 정보

- 역할: 로그인할 수 있는 사용자 정보를 저장합니다.
- 저장 항목: 아이디(`Id`), 이름(`Name`), 관리자·작업자 구분(`Role`), 비밀번호 해시(`PasswordHash`), 계정 활성 여부(`IsActive`).
- 예: worker1이라는 작업자 계정이 사용 가능한 상태인지 확인할 때 사용합니다.

로그인 판정은 서버의 처리 코드가 수행합니다. 이 클래스는 그때 사용할 정보의 형태를 정합니다. 비밀번호 원문 대신 해시를 저장합니다.

## 2. UserLineAccessEntity.cs — 사용자별 라인 접근 권한

- 역할: 사용자가 어느 라인에 접근할 수 있는지 저장합니다.
- 저장 항목: 사용자 아이디(`UserId`), 라인 번호(`LineId`).
- 예: worker1에게 1번과 2번 라인 권한이 있으면 두 건을 저장합니다.

실제 요청의 허용·거부는 서버가 이 정보를 확인해서 판단합니다. 같은 사용자에게 같은 라인 권한을 중복 저장하지 못하게 합니다.

## 3. LineEntity.cs — 라인 현황

- 역할: 생산라인의 현재 상태와 검사 누적 개수를 저장합니다.
- 저장 항목: 번호(`Id`), 이름(`Name`), 실제·가상 구분(`IsReal`), 가동 상태(`OperationStatus`), 검사 상태(`InspectionStatus`), 정상 개수(`NormalCount`), 불량 개수(`DefectCount`), 판정 불가 개수(`UndeterminedCount`), 갱신 시각(`UpdatedAt`).
- 예: 1번 라인은 가동 중이며 정상 100개, 불량 3개입니다.

초기 데이터는 대표 실제 라인 1개와 가상 라인 3개, 총 4개입니다. 실제 설비와 자동 연결되었다는 뜻은 아닙니다.

## 4. InspectionEntity.cs — 검사 결과 한 건

- 역할: 검사할 때마다 개별 결과를 기록합니다.
- 저장 항목: 검사 고유번호(`Id`), 라인 번호(`LineId`), 판정 결과(`Result`), 형태 점수(`ShapeScore`), 색상 점수(`ColorScore`), 판정 이유(`Reason`), 검사 시각(`InspectedAt`).
- 예: 1번 라인에서 오후 3시에 검사한 제품이 색상 점수 때문에 불량으로 판정됐습니다.

`LineEntity`는 누적 개수를, `InspectionEntity`는 검사 한 건씩의 상세 기록을 담습니다. 서버는 검사 기록과 해당 라인의 누적 개수를 함께 저장합니다.

현재 검사 API는 점수를 전달하는 시뮬레이션 방식입니다. YOLO 도입은 결정됐지만, YOLO 전용 결과 항목과 실제 영상 연결은 아직 반영하지 않았습니다.

## 5. IssueEntity.cs — 문제 정보와 현재 처리 상태

- 역할: 라인에서 발생한 문제의 내용과 현재 상태를 저장합니다.
- 저장 항목: 문제 고유번호(`Id`), 라인 번호(`LineId`), 문제 종류(`Type`), 제목(`Title`), 설명(`Description`), 현재 상태(`Status`), 등록자(`CreatedBy`), 마지막 조치 메모(`ActionNote`), 등록 시각(`CreatedAt`), 갱신 시각(`UpdatedAt`).
- 예: 1번 라인 장비 멈춤 문제가 현재 조치 중이며, 마지막 메모는 센서 점검 중입니다.

현재 서버의 작업자 처리 순서: 발생 → 확인 → 조치 중 → 완료 요청. 관리자는 완료 요청을 종결하거나, 사유와 함께 조치 중으로 반려할 수 있습니다. 종결 후에는 상태를 바꿀 수 없습니다.

이 순서와 변경 권한은 서버의 `AppStore`가 검사합니다. 초기 사용자 앱에는 확인 버튼이 없으므로 앱 담당자가 확인 처리를 연결해야 합니다.

## 6. IssueHistoryEntity.cs — 문제 상태 변경 이력

- 역할: 누가 언제 문제 상태를 어떻게 바꿨는지 변경할 때마다 기록합니다.
- 저장 항목: 이력 고유번호(`Id`), 문제 번호(`IssueId`), 이전 상태(`PreviousStatus`), 변경 후 상태(`NewStatus`), 변경자(`ChangedBy`), 변경 시각(`ChangedAt`), 조치 내용·반려 사유(`ActionNote`).
- 예: worker1이 오후 3시에 발생 상태를 확인 상태로 바꾸고, 문제를 확인했다는 메모를 남겼습니다.

`IssueEntity`에는 현재 상태를, `IssueHistoryEntity`에는 변경 과정을 여러 건으로 남깁니다. 서버는 상태와 변경 이력을 한 번의 저장으로 함께 반영합니다. 거절된 상태 변경 요청은 변경 이력으로 저장하지 않습니다.

## 7. IssueMessageEntity.cs — 작업자 문의와 관리자 답변

- 역할: 기존 문제 한 건에 연결된 작업자 문의와 관리자 답변을 메시지별로 저장하도록 정보 형태를 정합니다.
- 저장 항목: 메시지 번호(`Id`), 문제 번호(`IssueId`), 작성자 아이디(`SenderId`), 작성 당시 이름(`SenderName`), 작성 당시 관리자·작업자 구분(`SenderRole`), 메시지 내용(`Message`), 작성 시각(`CreatedAt`).
- 예: worker1이 특정 장비 문제에 ‘센서를 청소했는데도 멈춥니다’라고 문의하고, 관리자가 같은 문제에 답변을 남깁니다.

문제의 현재 상태나 상태 변경 이력과는 별도 기록입니다. AI 상담 기록도 아닙니다.

현재는 클래스·DB 등록·테이블 생성용 마이그레이션이 준비돼 있습니다. **문의 보내기·읽기 API와 앱 화면 연결은 아직 없습니다.** 테이블이 준비됐다고 메시지 기능이 완성된 것은 아닙니다.

## 8. AppDbContext.cs — EF Core의 DB 관리 클래스

- 역할: 사용할 테이블을 등록하고, 테이블 사이의 연결 규칙을 정합니다. 서버는 이 클래스를 통해 EF Core로 데이터를 조회·추가·수정합니다.
- 테이블 목록: `Users`, `UserLineAccesses`, `Lines`, `Inspections`, `Issues`, `IssueHistories`, `IssueMessages`.
- 연결 규칙: 사용자와 라인 접근 권한, 라인과 검사·문제, 문제와 변경 이력·메시지, 메시지와 작성자 등을 연결합니다.
- 중복 제한: 같은 사용자에게 같은 라인 권한을 중복으로 저장하지 못하게 합니다.
- 삭제 제한: 연결된 기록이 있는 사용자·라인·문제는 함부로 삭제하지 못하게 합니다.
- 메시지 규칙: 내용은 필수이고 길이는 1~2,000자입니다. 문제별 메시지 조회용 인덱스와 작성 시각 저장 형식도 설정합니다.

`AppDbContext` 자체는 별도 테이블이 아닙니다. 어느 테이블에서 무엇을 조회하거나 저장할지는 서버 코드에서 지정합니다.

## 기존 서버 클래스에서 연결한 부분

아래 클래스는 위의 ‘DB 클래스 8개’ 개수에 포함하지 않습니다.

### AppStore.cs — 데이터 조회·저장 처리

- 파일 위치: `Infrastructure/AppStore.cs`
- 기존 JSON 파일 대신 EF Core·SQLite로 사용자·권한·라인·검사·문제를 조회하고 저장합니다.
- 로그인 정보 확인, 사용자 등록·수정, 검사 결과와 누적 개수 저장, 문제 등록·상태 변경·변경 이력 저장을 처리합니다.
- 문제 상태 순서와 수행자의 권한을 검사합니다. 문의 메시지 처리 기능은 아직 연결하지 않았습니다.

### AuthService.cs — 로그인 토큰과 현재 권한 확인

- 파일 위치: `Infrastructure/AuthService.cs`
- 로그인 시 토큰을 만들고, 후속 요청마다 DB에서 계정 활성 여부·현재 역할·허용 라인을 다시 확인합니다.
- 토큰은 서버 메모리에 보관하며 만료 시간은 로그인 후 8시간입니다. 서버를 재시작하면 다시 로그인해야 합니다.
- 비활성 계정의 요청은 차단하며, 비활성 계정으로 확인된 토큰은 제거합니다. 로그아웃 API는 아직 없습니다.

### DatabaseInitializer.cs — DB 준비와 최초 기본 데이터 등록

- 파일 위치: `Infrastructure/DatabaseInitializer.cs`
- 서버 시작 때 `Database.Migrate()`를 호출해 미적용 마이그레이션을 반영합니다.
- 사용자와 라인이 모두 비어 있을 때 기본 관리자·작업자 계정, 라인 4개, 접근 권한을 등록합니다.
- 사용자나 라인이 이미 있으면 기본 데이터를 다시 넣지 않습니다.

현재 메시지 추가 마이그레이션은 기존 표를 삭제하지 않고 새 표를 만듭니다. 다만 앞으로 작성할 모든 마이그레이션의 데이터 보존까지 자동 보장하는 것은 아니므로 변경 내용을 검토하고 중요한 DB는 백업해야 합니다.

### Program.cs — 서버 시작 시 DB 연결 설정

- 파일 위치: 서버 프로젝트 루트의 `Program.cs`
- `App_Data/productionline.db`를 사용할 SQLite 연결과 `AppDbContext` 생성 기능을 등록합니다.
- 앱 구성 후 `DatabaseInitializer.Initialize`를 호출해 DB 준비와 최초 데이터 등록을 수행합니다.
- 기존 API 요청을 인증·권한 검사와 데이터 처리 코드에 연결합니다.

## 현재 진행 상태

- EF Core 패키지는 `8.0.32`를 사용합니다.
- 사용자·권한·라인·검사·문제·상태 변경 이력을 SQLite에 저장하는 코드가 구현됐습니다. 기존 JSON 기록을 자동으로 가져오는 이관 기능을 구현했다는 뜻은 아닙니다.
- 마이그레이션은 `InitialCreate`, `AddIssueMessages` 두 개입니다. 최신 서버는 시작할 때 미적용 항목을 자동 적용하도록 되어 있습니다.
- 메시지 표가 실제 사용자 DB에 적용됐는지는 해당 DB 또는 최신 서버 실행 결과로 확인해야 합니다. 이 문서만으로 실제 적용 여부나 저장 건수를 단정하지 않습니다.
- Claude는 서버 빌드 성공과 새 임시 DB 생성, 기존 DB 복사본에 메시지 표 추가 및 데이터 유지를 보고했습니다.
- Codex는 2026-10-18 GitHub 코드에서 DB 초기화 순서·메시지 마이그레이션·UTF-8 형식·Git 제외 설정을 확인했습니다. 이 검토에서 빌드·실행 시험을 다시 수행하지는 않았습니다.
- `App_Data`는 Git 제외 대상으로 설정되어 있습니다. 이는 파일을 삭제하는 설정이 아닙니다.
- 남은 작업: 문의 메시지 API·앱 연결, AI 상담 기록 저장 구조, YOLO 결과 계약·연결, 사용자 앱 확인 처리 연결, 실제 WinForms 및 두 PC 통합 시험입니다.
- 기본 AI 매뉴얼은 JSON 파일 유지 방침이며, 현재 이 7개 테이블에 매뉴얼 저장용 테이블은 없습니다.
