# 사용자 앱 수정 안내 — 확인 버튼 추가와 서버 상태 순서 연결

## 이 문서를 받은 사람 또는 GPT에게

우리 팀은 처음에 받은 같은 기본 프로젝트를 각자 수정하고 있습니다. 사용자 앱 담당자는 기존 `02_UserApp` 프로젝트를 수정합니다. 로그인·공용 DTO·서버 호출의 기본 틀은 이미 있으므로 새 앱이나 새 HTTP 통신 구조를 만들 필요가 없습니다.

김하균은 서버·DB를 담당하며, 작업 완료 후 서버 관련 파일을 별도로 전달할 예정입니다. 김하균의 GitHub에 접속할 필요는 없습니다. 이 문서는 기존 사용자 앱에 필요한 변경을 안내하는 자료입니다.

본인의 앱이 초기 코드에서 달라졌을 수 있으므로, 먼저 현재 파일을 읽고 기존 수정 사항을 보존하면서 필요한 부분만 연결해 주세요. 문서의 예시를 앱 전체에 덮어쓰지 마세요.

## 1. 왜 수정해야 하나요?

서버는 문제 상태를 다음 순서로만 변경하도록 구현되어 있습니다.

```text
발생 → 확인 → 조치 중 → 완료 요청 → 관리자 종결
```

초기 사용자 앱은 ‘확인’ 버튼이 없고, ‘점검 시작’에서 바로 `InProgress`를 요청합니다. 따라서 발생 상태에서 점검 시작을 누르면 서버가 409로 거절합니다.

사용자 앱에 ‘확인’ 버튼을 추가하고, 상태에 따라 버튼을 사용할 수 있도록 연결해 주세요. 서버의 순서를 완화하거나 DB를 수정하는 작업이 아닙니다.

## 2. 먼저 확인할 기존 파일과 함수

경로는 처음 받은 프로젝트의 상대 경로입니다.

| 파일 | 역할 / 확인할 부분 |
|---|---|
| `02_UserApp/ProductionLine.UserApp/Form1.cs` | 문제 목록·버튼·상태 변경 화면. 주 수정 대상 |
| `00_Shared/ProductionLine.Shared/Contracts.cs` | 기존 `IssueStatus`, `UpdateIssueStatusRequest`, `IssueDto` 확인 |
| `00_Shared/ProductionLine.Shared/ProductionLineApiClient.cs` | 기존 `UpdateIssueAsync`와 로그인 토큰·서버 주소 처리 확인 |

초기 코드에는 다음 함수가 있습니다. 본인 앱에서 이름이나 구조가 바뀌었다면 대응하는 위치에 연결하세요.

- `StartAction`: 점검 시작 → `InProgress` 요청
- `RequestCompletion`: 완료 요청 → `CompletionRequested` 요청
- `ChangeSelectedIssue`: 선택한 문제의 상태 변경 요청과 새로고침
- `SelectedIssue()`: 선택한 문제 조회

## 3. 버튼과 상태 연결

| 현재 문제 상태 | 확인 | 점검 시작 | 완료 요청 |
|---|---|---|---|
| 발생 `Occurred` | 사용 가능 | 비활성화 | 비활성화 |
| 확인 `Acknowledged` | 비활성화 | 사용 가능 | 비활성화 |
| 조치 중 `InProgress` | 비활성화 | 비활성화 | 사용 가능 |
| 완료 요청 `CompletionRequested` | 비활성화 | 비활성화 | 비활성화 |
| 종결 `Closed` | 비활성화 | 비활성화 | 비활성화 |

문제를 선택하지 않았거나 요청 처리 중일 때도 세 버튼을 비활성화하세요. 문제 선택 변경·목록 새로고침·상태 변경 성공 시 버튼 상태를 다시 계산하세요. 기존 문제 등록 버튼은 유지하고, 확인 버튼을 넣을 공간에 맞춰 레이아웃을 조정하세요.

관리자가 완료 요청을 반려하면 상태가 다시 `InProgress`로 돌아옵니다. `ActionNote`의 반려 사유를 표시하고, 추가 조치 후 재완료 요청이 가능하게 해 주세요.

## 4. 기존 호출 함수를 그대로 사용

공용 클라이언트에 이미 있는 함수입니다.

```csharp
Task<IssueDto> UpdateIssueAsync(
    Guid issueId,
    UpdateIssueStatusRequest request);
```

확인 버튼의 이벤트는 기존 공통 함수를 재사용할 수 있습니다.

```csharp
private async void AcknowledgeIssue(object? sender, EventArgs e)
{
    await ChangeSelectedIssue(
        IssueStatus.Acknowledged,
        "사용자가 문제를 확인함");
}
```

위 코드는 기존 `ChangeSelectedIssue`가 남아 있을 때의 연결 예시입니다. 버튼 생성·이벤트 연결·상태 검사·중복 클릭 방지까지 함께 구현해야 합니다.

직접 공용 함수를 부르는 형태라면 다음과 같습니다.

```csharp
var updatedIssue = await _api.UpdateIssueAsync(
    issue.Id,
    new UpdateIssueStatusRequest(
        IssueStatus.Acknowledged,
        "사용자가 문제를 확인함"));
```

기존 점검 시작은 `InProgress` 요청을 유지하되, 확인 상태에서만 사용하게 하세요. 메모는 `사용자가 점검을 시작함`처럼 확인 동작과 구분하면 됩니다. 완료 요청은 `CompletionRequested`를 유지하며, 가능하면 실제 조치 내용을 입력받아 전달하세요.

새 상태 enum·새 API·새 공용 호출 함수를 추가할 필요는 없습니다. 기존 로그인으로 받은 토큰을 사용하며 별도의 인증 구조를 만들지 마세요.

## 5. 서버 규격 — 연결 확인용

기존 `UpdateIssueAsync`가 아래 요청을 처리하므로 HTTP 코드를 중복 구현할 필요는 없습니다.

```http
PUT http://<서버PC-IP>:5050/api/issues/{문제ID}/status
Authorization: Bearer {로그인 응답으로 받은 토큰}
Content-Type: application/json
```

| 동작 | `status` | `actionNote` 예시 |
|---|---:|---|
| 확인 | 1 | 사용자가 문제를 확인함 |
| 점검 시작 | 2 | 사용자가 점검을 시작함 |
| 완료 요청 | 3 | 실제 수행한 점검 및 조치 내용 |

확인 요청 예시:

```json
{
  "status": 1,
  "actionNote": "사용자가 문제를 확인함"
}
```

기존 enum 값은 변경하지 않습니다.

```text
0 = Occurred             발생
1 = Acknowledged        확인
2 = InProgress          조치 중
3 = CompletionRequested 완료 요청
4 = Closed              종결
```

작업자는 `0→1`, `1→2`, `2→3`만 요청합니다. 관리자는 `3→4` 종결 또는 사유를 포함한 `3→2` 반려를 수행합니다. 작업자에게 종결 버튼이나 권한을 추가하지 마세요.

성공 응답은 HTTP 200과 변경된 `IssueDto`입니다. 필드는 `id`, `lineId`, `type`, `title`, `description`, `status`, `createdBy`, `actionNote`, `createdAt`, `updatedAt`입니다.

## 6. 새로고침·오류 처리

- 서버 성공 응답을 받은 뒤 화면 상태를 갱신하세요. 요청을 보냈다는 이유만으로 성공으로 표시하지 마세요.
- 성공 후 문제 목록을 새로 조회하고, 가능한 경우 선택한 문제를 ID 기준으로 유지하세요.
- 기존 공용 클라이언트는 서버 오류를 예외로 전달합니다. 이를 잡아 안내하고 필요한 새로고침을 수행하세요.

| 응답 | 뜻 | 화면 처리 |
|---|---|---|
| 400 | 잘못된 입력 | 서버 메시지 안내 |
| 401 | 로그인 필요·만료·계정 비활성화 등 | 재로그인 안내 |
| 403 | 기능 또는 라인 권한 없음 | 권한 없음 안내 |
| 404 | 해당 문제 없음 | 목록 새로고침 |
| 409 | 순서 불일치·같은 상태 재요청 등 | 메시지 안내 후 현재 상태 재조회 |

서버 오류 본문은 `{ "message": "안내 내용" }` 형태입니다. 네트워크 오류라면 요청이 서버에 반영됐는지 확실하지 않을 수 있으므로, 연결 복구 후 현재 상태를 조회하고 다음 행동을 결정하세요.

## 7. 서버 주소 설정

같은 PC에서 서버와 앱을 실행할 때는 기존 기본 주소 `http://127.0.0.1:5050`을 사용할 수 있습니다. 다른 PC에 있는 김하균 서버에 접속할 때는 실제 서버 PC IP가 필요합니다.

```text
http://<실제 서버PC-IP>:5050
```

기존 공용 클라이언트의 주소 선택 순서는 생성자 인수 → `PRODUCTIONLINE_SERVER_URL` 환경변수 → 기본 주소입니다. 환경변수를 바꿨다면 앱을 다시 실행하여 반영하세요. 실제 IP·포트·실행 방법은 서버 전달 때 김하균이 안내합니다. 예시 IP를 확정 주소로 쓰지 마세요.

서버가 실행 중이어야 하며, 다른 PC 접속은 네트워크와 서버 PC 방화벽 허용도 필요합니다. `localhost`는 앱을 실행한 자기 PC를 뜻합니다.

## 8. 담당 범위와 변경하지 않을 것

- 사용자 앱 담당: 버튼·입력·화면 표시, 기존 API 호출 연결, 오류 안내, 새로고침.
- 김하균: 서버 로그인·권한·상태 순서 검사, DB 저장과 변경 이력, 서버 파일 및 접속 안내 전달.
- 관리자 앱 담당: 완료 요청 확인·종결·반려 화면. 이번 사용자 앱 수정 범위 밖입니다.

이번 작업에서는 서버 코드·DB·마이그레이션·공용 enum/DTO를 변경하지 않습니다. 앱은 서버를 통해 요청하며 DB에 직접 연결하지 않습니다. 이 안내는 관리자 문의 메시지나 AI 상담 기능을 추가하라는 요청이 아닙니다.

## 9. 서버 전달 후 연결 시험

허용 라인이 있는 작업자 계정으로 다음을 확인하세요.

1. 새 문제를 등록하면 발생 상태이며 확인 버튼만 사용할 수 있다.
2. 확인을 누르면 확인 상태로 바뀌고 점검 시작 버튼을 사용할 수 있다.
3. 점검 시작 후 조치 중으로 바뀌며 완료 요청이 가능하다.
4. 완료 요청 후 작업자가 상태를 더 바꾸거나 종결할 수 없다.
5. 관리자가 사유와 함께 반려하면 사유가 보이고 재완료 요청이 가능하다.
6. 관리자 종결 후 상태 변경 버튼을 사용할 수 없다.
7. 앱 재실행·재로그인 후에도 서버에 저장된 상태가 표시된다.
8. 중복 클릭·다른 PC의 선행 변경·통신 실패가 생겨도 화면이 잘못된 상태로 남지 않는다.

완료 후 김하균에게 수정 파일 목록, 빌드 결과, 실제 연결 시험 결과와 남은 문제를 전달해 주세요. 시험하지 않은 항목은 미실행으로 표시하세요.
